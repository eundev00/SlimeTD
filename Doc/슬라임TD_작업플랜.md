# 슬라임 TD — 작업 플랜 (1인 개발, 단계별)

**전제 조건**
- 개발 인원: 1인 (기획/개발 담당, 아트는 유니티 에셋스토어 구매)
- 맵/프리팹 조립은 직접 진행
- 목표 범위: 스테이지 3개, 슬라임 4종(기본 3종 + 대장 슬라임 1종), 타워 2~3종

## 1. 기술 스택

| 역할 | 사용 기술 |
|---|---|
| 엔진 | Unity 6000.3.6f1 (URP 17.3) |
| DI | VContainer 1.17.0 |
| UI 패턴 | MVP (Model = Service, View, Presenter) |
| 이벤트 | MessagePipe (+ VContainer Integration) |
| 비동기 | UniTask 2.1.0 |
| Reactive | UniRx (`ReactiveProperty`, `CompositeDisposable`) |
| 프레임 업데이트 | UpdateSubscriptionService (중앙 집중 Update 관리) |
| 경로 이동 | Unity Splines (곡선 경로 생성/이동) |
| 트윈/연출 | DOTween (피격 반응, 분열 연출 등 "손맛" 구현) |

> Unity Object Pool, ScriptableObject는 엔진 기본 제공 기능이라 별도 스택으로 명시하지 않고, 각 단계 내 설계 패턴으로만 활용한다.

> 일정(기간)은 각자 상황에 맞춰 조절하고, 이 플랜은 **순서**만 참고한다. 각 단계 끝에 있는 체크포인트를 통과하면 다음 단계로 넘어가는 방식이라, 며칠 걸리든 항상 "플레이 가능한 상태"를 유지하며 진행할 수 있다.

---

## 0단계 — 아키텍처 기반 구축

**목표: 게임 로직을 짜기 전에, 프로젝트 전체를 지탱할 구조부터 세운다**

기술 스택(VContainer / MVP / MessagePipe / UniTask / UniRx / UpdateSubscriptionService)은 나중에 끼워 넣으려면 리팩토링 비용이 크기 때문에, 1단계 프로토타입을 만들기 **전에** 뼈대를 먼저 잡아야 한다.

- [ ] Unity 6000.3.6f1 + URP 17.3 프로젝트 셋업, 패키지 설치 (VContainer, UniTask, UniRx, MessagePipe, Unity Splines, DOTween)
- [ ] **VContainer** 루트 LifetimeScope 구성 (씬 스코프 / 프로젝트 스코프 분리 설계)
- [ ] **MVP 패턴** 기본 골격 작성 — Service(Model), View(MonoBehaviour), Presenter(중재자) 3계층 인터페이스/베이스 클래스 정의
- [ ] **MessagePipe** + VContainer 통합 세팅 — 이벤트 채널 등록 방식 확정 (예: `WaveStartedEvent`, `SlimeKilledEvent`, `LifeChangedEvent` 등 이벤트 네이밍 컨벤션 미리 정의)
- [ ] **UpdateSubscriptionService** 구현 — 개별 오브젝트가 각자 `Update()`를 쓰지 않고 이 서비스에 구독하는 구조로 통일 (슬라임 이동, 타워 타겟팅 등이 여기 붙는다)
- [ ] **UniRx ReactiveProperty** 적용 대상 정의 — 예: 골드, 라이프, 슬라임 체력 등 UI와 동기화되는 값들을 `ReactiveProperty`로 선언하고 `CompositeDisposable`로 구독 해제 관리 패턴 확립
- [ ] **UniTask** 적용 대상 정의 — 씬 전환, 웨이브 시작 딜레이, 리소스 로딩 등 비동기 처리 지점 정리
- [ ] 위 구조로 "빈 화면에 버튼 하나 → 이벤트 발행 → Presenter가 UniRx 값 갱신 → View 반영"까지 되는 최소 샘플 1개로 아키텍처 동작 검증

**체크포인트**: 실제 게임 로직 없이도, 이벤트 발행 → Reactive 값 변경 → UI 갱신까지 이어지는 배관(plumbing)이 한 번은 끝까지 동작해야 한다. 이것이 확인되면 이후 단계부터는 이 구조 위에 기능만 얹으면 된다.

---

## 1단계 — 기반 세팅 & 프로토타입 코어

**목표: 슬라임 하나가 경로를 걷고, 타워 하나가 쏘는 최소 동작 확인**

> 아키텍처 적용: 슬라임 이동은 `Unity Splines`(`SplineContainer` + `SplineAnimate`)로 곡선 경로를 따라가도록 구현하고, 이동 갱신은 `UpdateSubscriptionService`에 구독한다. 타겟팅 대상 탐색 로직은 Service(Model) 계층에 두고 View는 순수 표현만 담당한다.

- [ ] 유니티 프로젝트 셋업, 필요 에셋 구매/임포트 (슬라임 리소스, 이펙트/사운드 에셋 후보 탐색)
- [ ] 슬라임 프리팹 기본형 1종 구성 (재질+얼굴 조합 테스트)
- [ ] Spline 경로 1개 제작 + 슬라임이 곡선 경로 따라 이동하도록 연결
- [ ] 타워 프리팹 1종 + 가장 가까운 슬라임 타겟팅 + 발사체 로직
- [ ] 슬라임 피격 → 체력 감소 → 소멸 (분열 로직은 다음 단계에서 처리)

**체크포인트**: 슬라임 1종 + 타워 1종으로 "쏘면 죽는다"가 동작하면 성공

---

## 2단계 — 핵심 루프 완성 (골드/라이프/웨이브)

**목표: 라운드 단위로 돌아가는 최소 게임 루프**

> 아키텍처 적용: 골드/라이프는 `ReactiveProperty`로 선언해 UI가 자동 반영되도록 구성한다. 웨이브 시작/종료, 게임오버는 `MessagePipe` 이벤트로 발행하고 Presenter가 구독해서 처리한다.

- [ ] 웨이브 스포너 (일정 시간마다 슬라임 스폰, 웨이브 종료 판정)
- [ ] 골드 시스템 (처치 시 골드 획득)
- [ ] 라이프 시스템 (경로 끝 도달 시 라이프 차감, 0되면 게임오버)
- [ ] 타워 배치 UI (골드 소모해서 맵에 배치)
- [ ] 웨이브 시작 버튼 / 웨이브 간 대기시간

**체크포인트**: 웨이브 3~5개 정도를 라이프 관리하며 클리어/실패까지 플레이 가능

---

## 3단계 — 슬라임 종류 확장 & 분열 시스템

**목표: 슬라임 종류 3종 + 분열(찌그러져 쪼개지는) 메커니즘 구현**

> 아키텍처 적용: 슬라임 체력을 `ReactiveProperty`로 두고 임계치 도달 시 `SlimeSplitEvent`를 발행한다. 별도 SplitService(Model)가 이를 구독해서 자식 슬라임 스폰을 처리한다. View(애니메이션)는 이벤트 결과만 받아 `DOTween`으로 찌그러짐/튕김 연출을 재생한다.

- [ ] 슬라임 종류 2~3종 추가 (속도/체력 다른 변형, 재질 다르게 적용)
- [ ] 분열 로직: 일정 체력 이하 시 작은 슬라임 2마리로 스폰 후 소멸
- [ ] 피격 시 찌그러짐/튕김 애니메이션 (`DOTween` 스케일 펀치/이징)
- [ ] 슬라임 종류별 라이프 차감량 임시 값 지정 (추후 밸런싱)

**체크포인트**: 슬라임을 때리면 쪼개지고, 쪼개진 슬라임도 다시 처치 가능해야 한다

---

## 4단계 — 타워 2~3종 완성 & 업그레이드 기초

**목표: 역할이 다른 타워 2~3종 + 간단한 업그레이드 1단계**

> 아키텍처 적용: 타워 업그레이드 시 스탯 변경은 Service 계층에서 처리 후 `ReactiveProperty`를 갱신하고, UI(View)는 구독만 한다. 타워 종류별 Presenter는 공통 베이스 클래스로 통일해 확장성을 확보한다.

- [ ] 타워 2종 추가 (예: 스플래시형, 슬로우형)
- [ ] 타워 업그레이드 UI (레벨업 시 스탯 소폭 상승, 트리는 나중에 확장 가능하게 구조만 마련)
- [ ] 타워 판매/재배치 기능
- [ ] 타워-슬라임 상성(있다면) 임시 적용

**체크포인트**: 서로 다른 타워 조합으로 웨이브 클리어 전략이 생겨야 한다

---

## 5단계 — 대장(보스) 슬라임 & 웨이브 디자인

**목표: 보스 슬라임 등장 + 웨이브 난이도 곡선 잡기**

- [ ] 대장 슬라임 프리팹 (대형 스케일, 체력 매우 높음, 처치 시 다량 분열)
- [ ] 웨이브 구성표 초안 작성 (스테이지 3개 각각 웨이브 순서/구성)
- [ ] 웨이브 난이도 점진 상승 (슬라임 수/속도/체력 조정)

**체크포인트**: 스테이지 1개를 처음부터 끝까지(보스 포함) 클리어 가능해야 한다

---

## 6단계 — 맵 3개 조립 & 스테이지 연결

**목표: 스테이지 선택 → 플레이 → 결과 화면까지 흐름 완성**

> 아키텍처 적용: 씬 전환/스테이지 데이터 로딩은 `UniTask`로 비동기 처리한다. 스테이지별 LifetimeScope를 분리해 씬 전환 시 이전 스테이지의 구독을 `CompositeDisposable`로 깔끔하게 해제한다.

- [ ] 맵 프리팹 조립 + 스테이지별 `Spline` 경로 배치 (곡선/갈림길 형태 포함) — 스테이지당 2~3일
- [ ] 스테이지 선택 화면 UI
- [ ] 스테이지 클리어/실패 결과 화면
- [ ] 스테이지별 웨이브 데이터 연결

**체크포인트**: 메인 화면 → 스테이지 선택 → 플레이 → 결과 화면, 전체 흐름이 끊김 없이 동작해야 한다

---

## 7단계 — 사운드/이펙트/폴리싱

**목표: "손맛" 다듬기 — 이 프로젝트에서 가장 중요한 구간**

- [ ] 피격/분열/처치 이펙트 연결 (파티클 + `DOTween` 스케일 펀치 등)
- [ ] 사운드 연결 (타격음, 분열음, 배치음, BGM)
- [ ] UI 폴리싱 (버튼 반응, 골드/라이프 표시 애니메이션)
- [ ] 전체 밸런스 1차 조정 (체력/데미지/골드 수치)

**체크포인트**: 플레이했을 때 "때리는 맛"이 느껴져야 한다

---

## 8단계 — 통합 테스트 & 빌드

**목표: 버그 수정 + 실제 기기 빌드 확인**

- [ ] 전체 플레이스루 테스트 (버그/밸런스 문제 기록)
- [ ] 크래시/성능 이슈 점검 (모바일 빌드 시 프레임/발열 체크)
- [ ] 우선순위 높은 버그 수정
- [ ] 최종 빌드 및 배포 준비 (스토어 등록용 스크린샷/설명 등은 별도 일정)

**체크포인트**: 처음 켜서 끝까지 크래시 없이 플레이 가능한 빌드 완성

---

## 진행 관리 팁

- 시간이 부족하면 **5단계(보스)**를 단순화(체력만 높은 버전으로)해서 줄일 수 있다.
- 가장 예상보다 오래 걸릴 가능성이 높은 단계는 **3단계(분열 시스템)**와 **7단계(폴리싱)**다. 이 두 단계는 여유를 두고 접근하는 것이 좋다.
- 각 단계 체크포인트를 넘길 때마다 "지금 상태로 처음부터 끝까지 플레이가 되는가"를 확인해야 한다 (버티컬 슬라이스 유지).
- **0단계(아키텍처)는 절대 건너뛰지 않는다.** MVP + DI + 이벤트 기반 구조는 처음엔 답답하게 느껴질 수 있지만, 슬라임 종류/타워 종류가 늘어나는 3~4단계부터 왜 이 구조가 필요한지 체감하게 된다. 반대로 0단계 없이 1단계부터 시작하면 나중에 갈아엎어야 할 확률이 높다.
- `CompositeDisposable` 해제 누락은 씬 전환 시 메모리릭/중복 이벤트의 흔한 원인이므로, View/Presenter가 파괴될 때 항상 해제되는지 초반에 패턴을 확립해둔다.
